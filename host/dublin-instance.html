Note 01 · Infrastructure

The instance was in Dublin

06 September 2026AmsterdamJordi Lluis

I created an AWS Lightsail instance in eu-west-1 (Dublin), Ubuntu, for the live Polybow path and later for daily recordings. That is a real host I paid for and operated. It is not a region benchmark. I did not run the same clock in a second city and compare.

Why a new box

The work on the submit path was to remove avoidable waits: a warmed HTTP/2 client, coincurve signatures, token metadata cached so it was not fetched on the hot path. Book updates could trigger an evaluation instead of waiting for the next poll. The per-market gate moved from 50 ms to 5 ms. That number is a throttle in code, not measured end-to-end latency.

The statistic I still have

The archived timer started at metadata preparation and stopped when the API answered. It is prepare + POST. It is not the earlier signal, not a confirmed fill, and not settlement.

Complete LAT_DETAIL rows, 3 May 2026
StratB sample52 complete records. Median 35.35 ms. p95 298.0 ms. 51 of 52 replies were resting, not immediately matched.
UC sample22 complete records. Median 33.0 ms. p95 289.2 ms. All 22 resting.
What “p95” is hereThe 95th percentile of that prepare-plus-response window in those files. It is not exchange latency and not fill latency.
Conclusion I will defend: a fast acknowledgement from Dublin is not a fill. Creating the instance is evidence that I can stand up a VPS, run a process, and define a clock. It is not evidence that Dublin made the strategy better. I deleted the VPS recordings. The public repository keeps the ledger script and the timing parser, not those days.

If a recruiter only needs one sentence: I provisioned Lightsail, I defined the window I measured, and I kept the loss in the postmortem.
